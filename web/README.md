# Model Torrent — static web catalog

Anonymous, no-login catalog UI. Reads `catalog.json` and per-model manifests from this directory.

## Serve locally

From the repo root:

```bash
cd web
python3 -m http.server 8080
```

Open [http://localhost:8080/](http://localhost:8080/).

Alternatively, when implemented:

```bash
mt catalog
```

will serve the same files (fixtures under `testdata/fixtures/` back the demo SHA-256 entries).

## Browser download (WebTorrent)

Each model card includes a **Download in browser** button. Clicking it:

1. Parses the model's magnet URI from the loaded catalog.
2. Starts a [WebTorrent](https://webtorrent.io/) download in the page (loaded from jsDelivr CDN).
3. Shows live progress: percent complete, bytes downloaded/total, peer count, and download speed.
4. On completion, renders **Save file** links (one per torrent file) using blob URLs.

Cards also show:

- The full magnet URI (click or **Copy** to clipboard)
- SPDX license from the catalog
- Per-file SHA-256 checksums from each model's `manifest.json`
- Swarm health from `health.json` plus a live peer count during an active browser download

### Placeholder magnets

Demo entries that are not yet magnetized use obvious placeholder infohashes (e.g. containing `1220a1b2c3d4` or `1234567890abcdef`). The UI detects these patterns and **disables** the browser-download button with a short explanation.

### No live seeders

If WebTorrent finds **zero peers** after a ~15 second grace period, the card shows:

> No live seeders — try `mt get <modelId>` from CLI

instead of hanging indefinitely.

### Known limitation: WebRTC / WSS only

WebTorrent in the browser connects to peers over **WebRTC** and to webseeds over **WebSocket (WSS)**. A plain BitTorrent client seeding via TCP/UDP **will not** connect to the browser unless there is also:

- a WebRTC-capable peer, or
- a WebSocket tracker / WSS webseed in the magnet

For the demo, **`demo/tiny-gguf`** has a real magnet, but browser download still requires someone to seed in a WebTorrent-compatible way (or a WSS webseed). Seeding with `mt get` alone uses classic BitTorrent wire protocol and may not satisfy the browser swarm. Use the CLI (`mt get`) for reliable fixture fetch during development; treat in-browser download as the production UX path once WSS webseeds or WebRTC seeds are available.

## Demo data

Bundled entries use fake model IDs (`demo/tiny-safetensors`, `demo/tiny-gguf`, `demo/tiny-bundle`). File hashes match the 64 KB fixtures from `make fixtures`.

**`demo/tiny-gguf`** ships a **real BitTorrent magnet** (generated by `scripts/gen_web_magnets.go`). Bootstrap download uses catalog-relative `file://fixtures/…` webseeds; after fetch, `mt get` seeds the swarm (real magnet path, not fixture dev mode).

```bash
make fixtures   # regenerates magnets + copies bytes into web/fixtures/
MT_CATALOG=web/catalog.json ./bin/mt get demo/tiny-gguf ./dest
```

The other demo entries still use placeholder magnets until they are magnetized the same way.

## Empty catalog

If `catalog.json` is missing or has zero models, the page shows instructions to run `make fixtures` and `mt catalog`.
